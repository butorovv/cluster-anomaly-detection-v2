# Аудит Cluster Monitor V3.2

Локальная копия и ВМ начинали с чистой `feature/qt-gui` на SHA `594e42adaf709e7e0c1529528381de8ae5204de3`. Локальные `main` и `origin/main` указывают на разные коммиты (`9b3a0cf` и `782d401`). Для V3.2 используется продолжение существующей feature-ветки. Сборки и испытания выполняются на ВМ.

## Среда

На Ubuntu 24.04 установлены GCC 13.3, CMake 3.28.3, Qt 6.4.2. Исполняемый файл связан с Qt Core, Gui, Widgets и Network, Qt загружает DBus как зависимость. Приложение устанавливает Fusion и общие QSS. Системный шрифт sans-serif на ВМ — DejaVu Sans. VNC :11 на момент аудита работал в 1536×1060 при 96 DPI, доступны 1360×768 и 1920×1080. VNC слушает 127.0.0.1 и ::1, Master D2 опубликован только на 127.0.0.1:18084. PostgreSQL и Kafka этого проекта остаются внутри сети Compose.

## Референс и исходная реализация

Изучены приложенные Cluster_Monitor_V32.html и Cluster_Monitor_V32_FULL_TZ.md. В HTML проверены CSS основного макета и адаптивных правил, отдельные стили календаря и устройства, структуры экранов и обработчики навигации, модального окна, фильтра, гистограммы, временной шкалы и наведения. Массивы событий, узловые свидетельства и физические значения в HTML иллюстративны.

- UX‑1 был реализован в V2. Сохраняются боковая навигация, оболочка, QSS, карточки сценариев и штатные страницы.
- UX‑2 был реализован для трёх равноправных вкладок. Для V3.2 нужны иерархические переходы, последние завершённые события в обзоре, матрица узлов и постоянно раскрытые основные показатели.
- В журнале V2 был модальный выбор диапазона, фильтр по пересечению и четыре столбца. V3.2 требует общий встроенный редактор даты и времени UTC, фильтр [начало, конец) по старту события, гистограмму, пять столбцов и CSV.
- UX‑3–UX‑5 на исходном SHA не завершены. GUI открывает проверенные демозапуски по метаданным, управление запуском в `gui/demo.ps1` доступно из CLI. Каталог зависит от двух конкретных папок; экспорт отключён. UX‑6 ранее подтвердил сохранённый D2, но не сценарии V3.2.

## Контракты реальных данных

- Master публикует Raw, RBI2TemporalResult и необязательный RBI2Evidence. Raw.R содержит определяющую пару и свидетелей; Raw.B содержит только групповое состояние, оценку и порог. Для B узловая локализация отсутствует. temporal.local_i2 и Raw.Local дают локальные сведения об IF. Это не самостоятельный голос и не индивидуальное решение I2. Raw.IF содержит межгрупповое обогащение; UUID и временные ссылки свидетельств остаются техническими данными.
- Master не отдаёт устройство/канал: Raw.host_values в живом ответе содержит пять производных признаков. Исходный F18-v1 Parquet (89 МиБ) соответствует зарегистрированному SHA256 `cf3fa634448b7147209bebf3b1c20a1a031be5c047678083adda10581ff562e7`. Схема включает две температуры/мощности CPU, шесть температур/мощностей GPU и две мощности PSU. Пропуски представлены nullable-каналами и availability_mask. Требуется чтение только узла и ограниченного окна из неизменяемого архива, привязанного к фактическому источнику запуска; публиковать Master, Kafka или PostgreSQL для GUI не требуется.
- Существующий demo-runner использует PowerShell, Compose и метаданные каталога с уникальным execution_id. Он уже проверяет готовность компонентов, завершение Replayer, финализацию и сверяет страницы REST. На ВМ Docker вызывается существующим служебным адаптером; обычный пользователь не может работать с Docker socket напрямую. Для GUI необходимо переиспользовать подготовленный оператором адаптер и ограниченный lifecycle, не наделяя приложение новыми системными правами.
