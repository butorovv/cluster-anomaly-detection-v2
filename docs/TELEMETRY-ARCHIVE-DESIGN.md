## Два независимых контура

- Диагностика: Kafka → Worker → существующий транспорт результатов → Master.
- Физические данные: одноразовый импорт Summit или независимый Kafka Consumer →
  PostgreSQL. Read-only REST разрешает только пересечение опубликованных тиков и
  покрытия архива. GUI запрашивает все 18 каналов через REST.

В исходном режиме испытаний архивный стек не запускается. В режиме reuse
исполнения с идентичным источником читают один проверенный импорт. В режиме
streaming отметки наблюдений, покрытие тика и архивная позиция принадлежат
исполнению, а физические значения уникальны для источника и датчика.

## Архив и идентичность

V1 применяется без изменений в выделенной архивной базе. Служебные миграции
архива имеют самостоятельную историю и применяются отдельно от диагностической
схемы. В одной архивной БД регистрируется один источник. Физический ключ V1
`(metric_source_id, ts)` позволяет разным исполнениям одного источника
использовать те же значения. Другой источник требует отдельной БД.
Хеш Parquet относится к исходному артефакту F18-v1, хеш топологии — к
каноническому списку групп и узлов. CPU mean и GPU core — подготовленные
физические каналы F18.

Импорт читает проверенный Parquet с того же дескриптора, применяет существующую
проверку сетки full-grid, пакетный Writer и проверку равенства значений.
Манифест готовности публикуется после окончания загрузки, проверки каждого
группового тика и количества строк. Повтор готового импорта использует
манифест. Неоконченная загрузка возобновляется идемпотентной записью.

Для архиватора требуется одна PostgreSQL-транзакция на подтверждаемую единицу
работы. Она должна включать запись измерений, компактное покрытие тика и
продвижение архивного offset под fencing. Диагностические checkpoints для
архиватора не используются. Для REST живое исполнение подтверждает тики по
финальным строкам Master, история использует проверенный каталог сохранённых
страниц. У действующего Master и архива разные права доступа.
