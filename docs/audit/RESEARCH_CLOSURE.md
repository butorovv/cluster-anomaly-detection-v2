## Локальное измерение

`TestTimestampSQLMeasurements/-v9` на PostgreSQL 17.5 с `fsync=on` и `synchronous_commit=on`. Три повтора по 384 fragment transactions после прогрева. При обработке одного timestamp за раз получилось 212–239 tx/s (медиана 229), при четырёх независимых timestamps — 437–583 tx/s (медиана 452). Все шесть повторов дали 24 полных join на измеряемом участке и одинаковый digest payload и MessageID. В наблюдавшихся снимках не было lock waits, суммарное ожидание свободного соединения в пуле равно нулю. Этот тест не воспроизводит Kafka poll-wave, параллельный поток Worker и storage новой ВМ.

`TestSQLMicroMeasurements` в режиме `locks` отдельно удерживал финальный join при записи Worker checkpoint. В шести итерациях не зарегистрированы lock wait или timeout. Проверка lease fencing прошла. Это ограниченный локальный опыт. Насыщение WAL, I/O или CPU брокера в W1/W4 не измерено. Изолированного локального брокера нет, поэтому Kafka W1/W4, performance A/B и `performance_candidate` отложены до измерения с backlog.

## Следующий замер

Включить `CAD_MASTER_DIAGNOSTICS=1` только для короткой изолированной серии. При той же ревизии и фиксированных 16 партициях, Master concurrency 4 и batch 16 сделать по три чередующихся W1/W4 на одном заранее заданном окне и схеме. Дать очереди вырасти, затем дождаться её опустошения. Все ожидаемые fragment IDs, joins, финальные offsets, отсутствие дублей и ожидаемый digest задать до запуска.

Сопоставить интервалы при устойчивом `group.results` backlog. Основная метрика — разница durable SQL `next_offset` за секунду, включая записи, для которых Master подтвердил только движение позиции. Сохранять `/metrics` Master или `metrics-samples.json`, активные ожидания PostgreSQL с разбивкой по роли, эффективные параметры PG и квоты брокера, его CPU и throttling. Для WAL сохранить разность счётчиков `pg_stat_wal` и время WAL write/sync при включённом на обеих конфигурациях `track_wal_io_timing`.

- Для Kafka сравнить `poll_wait`, batch, число разных партиций и peak handlers, длительность и самый долгий job волны, суммарную занятость handlers, gap до следующего poll и auxiliary commit. Последний входит в gap. Полезная загрузка в окне оценивается как сумма handler-seconds, делённая на длительность окна и настроенную concurrency.
- Для SQL сопоставить `master_pg_*` с ожиданиями PG. Join измеряется от входа в обработку последнего fragment до записи join marker. SQL-время — сумма клиентских pgx вызовов в теле join, включая ожидание и чтение строк. Среднее число вызовов на join — `master_pg_join_sql_round_trips / count(master_pg_join_sql_duration)`. Advance offset и COMMIT происходят после тела join. У COMMIT есть отдельный таймер, который включает ожидания помимо WAL.
- Backlog по партиции — Kafka `ListEndOffsets` минус SQL `next_offset`. Сначала опрашивается SQL, затем Kafka, поэтому это разнесённые во времени снимки. Неполные или несовпавшие снимки помечаются недействительными. Интервалы вычислять по timestamp Master, пропускать повторы backlog timestamp и сброс счётчиков при смене PID.

Когда ограничение воспроизводится, сравнить тот же инструментированный код и код с одной правкой. Исторические W1/W4 служат ориентиром. При будущей полной приёмке сохранить 46 080 group-ticks, 2 880 joins, 750 parent anomaly events, 1 284 positives, 16 finalized checkpoints и сверку с независимым golden.
